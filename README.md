# NoName — Django-маркетплейс независимых брендов (v3)

Готовый локальный MVP: чёрная типографическая главная без рисунка футболки в герое, бренды, каталог с фильтрацией, активные/отсутствующие размеры, корзина с выбором доставки, гостевое оформление заказов, история покупателей, кабинеты менеджеров брендов и панель администратора с аналитикой.

**Внимание:** это программный прототип, а не готовый публичный магазин. Онлайн-оплата, интеграция тарифов СДЭК/Почты России и уведомления пока не подключены. Остатки по размерам и предзаказы поддерживаются, а заказы обрабатываются вручную. Варианты доставки, включая пометки «демо», используют примерные, **неофициальные** тарифы, редактируемые в Django Admin.

## Быстрый запуск

Python 3.10+.

macOS / Linux:

```bash
cd noname_store
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py createsuperuser
python manage.py seed_demo
python manage.py runserver
```

Windows PowerShell:

```powershell
cd noname_store
py -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py createsuperuser
python manage.py seed_demo
python manage.py runserver
```

Открыть `http://127.0.0.1:8000/`.

`seed_demo` необязательна. Она создаёт/использует бренд «ПУСТОТА» и добавляет четыре демонстрационные футболки. Статические HTML-превью из каталога `previews/` можно открыть без Django, но это **нерабочие макеты**. Точка входа — `previews/preview.html`.

## Обновление из ПУСТОТА v2 — сохраняем данные

1. Скопируйте старые `db.sqlite3`, `media/` и конфигурацию секретного ключа/переменных окружения в резервную папку.
2. Распакуйте новый проект. **Не заменяйте** старую `db.sqlite3` пустой базой и **не удаляйте** `media/` с изображениями.
3. Перенесите базу и `media/` в папку с `manage.py` обновлённого проекта.
4. Запустите в виртуальном окружении `python manage.py migrate`, затем `python manage.py runserver`.
5. Все старые товары получат бренд «ПУСТОТА» (миграция `0004`). Заказы, пользователи, фотографии, цены и история сохраняются. `0005` фиксирует название бренда в новых и существующих позициях заказа, `0006` добавляет несколько примеров конкретных служб доставки, не удаляя старые способы.

После обновления проверьте карточки, тарифы и заказ с тестовыми контактами.

## Управление брендами

1. Менеджер регистрируется на `/brand/register/` только с логином, e-mail и паролем. Бренд на этом шаге не нужен. В `/admin/` → **Менеджеры брендов** появляется заявка, а в списке пользователей аккаунт отмечен как менеджер.
2. Администратор подтверждает заявку в `/admin/`. До подтверждения кабинет и создание бренда закрыты.
3. После входа через `/brand/login/` подтверждённый менеджер без бренда попадает на `/brand/create/`. Он может создать только один бренд; редактирование названия и описания через кабинет не предусмотрено.
4. У одного бренда может быть несколько менеджеров. Администратор привязывает дополнительную подтверждённую заявку к существующему бренду через поле «Бренд» в **Менеджерах брендов**.
5. В кабинете доступны `/brand/products/`, `/brand/orders/` и статистика по моделям. Менеджер создаёт, редактирует, удаляет и восстанавливает только товары своего бренда. Поле бренда и подмена POST-запроса не позволяют назначить товар чужой марке.
6. В заказах менеджер видит только позиции своего бренда и их сумму, без стоимости доставки и чужих товаров. Доступны фильтры по товару и статусу. Общий статус заказа меняет только администратор магазина.
7. Администратор по-прежнему может использовать `/products/add/`, выбирать любой бренд и отмечать товары для главной. Менеджер не управляет выводом на главной.
8. Удаление бренда доступно менеджеру через `/brand/delete/` и требует точного названия и пароля. Это мягкое удаление: бренд и товары скрываются, кабинет закрывается, а заказы сохраняются.
9. В каталоге можно фильтровать вещи по бренду. В бегущей строке показываются **только активные, неудалённые бренды, у которых есть опубликованные товары**.

## Размеры, остатки и предзаказ

На странице вещи **и на карточках каталога** выводится ряд XS / S / M / L / XL / XXL / 3XL (плюс нестандартные размеры). Менеджер задаёт остаток каждого размера отдельно в форме товара. Первоначально **не выбран ни один размер**; сервер повторно проверяет размер, остаток и режим заказа, поэтому их нельзя подменить через HTML.

При оформлении обычного заказа остаток списывается атомарно. При отмене он возвращается один раз; повторно открыть отменённый заказ нельзя. Если включён предзаказ, размер с нулевым остатком можно оформить с пометкой «Под заказ» и указанным сроком изготовления. Предзаказ не списывает складской остаток, а его режим и срок сохраняются в позиции заказа.

## Заказ покупателя без регистрации

1. Открыть `/catalog/`, выбрать размер на карточке или странице товара, добавить вещь в `/cart/`.
2. В корзине сначала идут вещи и сумма товаров, **ниже выбирается доставка или самовывоз**, затем показывается сумма вместе с доставкой.
3. После нажатия «Продолжить оформление» выбранный способ сохраняется в сессии, а в `/checkout/` требуется только имя, e-mail, телефон и, если нужно для выбранной доставки, адрес. Смена доставки — назад через `/cart/`.
4. На сервере цены и метод доставки проверяются повторно. Создаётся заказ с зафиксированными названиями брендов, товаров, размерами, ценами, доставкой и итоговой стоимостью.
5. Гость видит страницу подтверждения по номеру в том же браузере, где оформил заказ. Номер заказа **не даёт доступ другим посетителям**. После очистки cookie или на новом устройстве гость не сможет открыть историю заказов; для полноценного поиска по e-mail нужны дополнительные безопасные ссылки и уведомления.
6. Зарегистрированный пользователь по-прежнему видит свои заказы через `/orders/`.

## Доставка

Через `/admin/` → **Способы доставки** можно менять название службы, стоимость, примечание, необходимость адреса, активность и порядок.

После применения миграций обычно видны следующие примеры:

| Способ | Примерная стоимость (настроить перед продажами) |
|---|---:|
| Самовывоз (после согласования) | 0 ₽ |
| СДЭК — пункт выдачи (демо) | 350 ₽ |
| Почта России (демо) | 390 ₽ |
| СДЭК — курьер (демо) | 650 ₽ |

Это выбор названия службы, **не** реальный заказ перевозки и **не** API-подключение. Пункты выдачи, трекинг, география и расчёт по адресу пока не реализованы. Перед коммерческой работой замените демонстрационные тарифы и подтвердите адрес самовывоза.

## Администратор и менеджер

| Страница | Функция |
|---|---|
| `/admin/` | Создание брендов, подтверждение менеджеров, настройки доставки, пользователи и все модели |
| `/products/add/` | Добавление товара с брендом, фотографиями и размерами |
| `/dashboard/products/` | Управление всеми вещами, редактирование, мягкое удаление и восстановление |
| `/dashboard/orders/` | История зарегистрированных и гостевых заказов, статусы |
| `/dashboard/` | Общая статистика магазина по каждой модели и бренду |
| `/brand/` | Статистика менеджера по заказам и товарам его бренда |
| `/brand/products/` | Товары только своего бренда |
| `/brand/orders/` | Заказы с фильтрами по товару и статусу |
| `/orders/` | История заказов зарегистрированного покупателя |

Удаление товара из каталога остаётся мягким, его старые заказы и статистика не исчезают. Отчёты по суммам относятся к **оформленным, не отменённым заказам, а не к оплаченным покупкам**.

## Безопасность и production

* Для публикации задайте уникальный `DJANGO_SECRET_KEY`, `DJANGO_DEBUG=0` и реальные `DJANGO_ALLOWED_HOSTS`. При выключенном debug автоматически включаются Secure cookies, HTTPS-редирект и HSTS на один час.
* Если HTTPS терминируется на reverse proxy, передайте `X-Forwarded-Proto: https` только от доверенного прокси и установите `DJANGO_TRUST_X_FORWARDED_PROTO=1`. Не включайте этот параметр при прямом доступе клиентов к Django.
* `DJANGO_SECURE_HSTS_INCLUDE_SUBDOMAINS=1` и `DJANGO_SECURE_HSTS_PRELOAD=1` включайте только после проверки HTTPS на всех поддоменах. При необходимости задайте `DJANGO_CSRF_TRUSTED_ORIGINS` со схемой, например `https://shop.example.com`.
* POST-запросы входа покупателя, менеджера и Admin ограничены 10 попытками за 5 минут, регистрация — 5 в час, оформление заказа — 10 в час с одного IP. Для нескольких процессов или серверов настройте общий production cache (Redis/Memcached); встроенный LocMemCache хранит счётчики отдельно в каждом процессе.
* Управление глобальными разделами сайта использует отдельные Django permissions: просмотр/изменение заказов и добавление/изменение/удаление товаров. Выдавайте их через группы в Admin. Одного флага `is_staff` недостаточно.
* Доступ менеджера к кабинету определяется подтверждённой записью **Менеджер бренда**, а не `is_staff`. Все товары, заказы, детали и операции проверяются на сервере по связанному бренду. Менеджер не получает права на общую административную панель и смену статуса заказа.
* Фотографии проверяются на сайте и в Admin: JPEG, PNG или WebP, до 8 МБ, до 8000 пикселей по стороне и до 24 мегапикселей.

## Что обязательно добавить перед публикацией

* Задать реальные production-переменные, настроить HTTPS у веб-сервера и проверить `python manage.py check --deploy`.
* Общий cache для rate limiting, дополнительный антиспам, подтверждение e-mail/телефона, уведомления и безопасные ссылки на гостевые заказы.
* Подключение реальных сервисов доставки, проверка тарифа и пунктов выдачи.
* Оплата через лицензированного провайдера, фискализация, политика конфиденциальности, оферта и возвраты.
* PostgreSQL, резервные копии, production-хранение изображений, антивирусная проверка файлов и двухфакторная аутентификация администраторов.

Проект — удобная стартовая база для развития NoName, но в текущем состоянии не следует принимать реальные платежи и рассчитывать на автоматическую доставку.
